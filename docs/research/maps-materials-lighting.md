# Maps, materials and lighting

What the human and Claude worked out on 2026-11-05, after calling increment 10 the baseline. Map work gates rendering work, so this comes first. It's research input, not a design: nothing here is built or accepted, and a proposal has to come next.

From here the engine diverges from Quake. Quake stays a fixture, and strict compatibility isn't a goal.

Each section separates what the human decided from what's only suggested. Costs come from other engines and need measuring here, on a GTX 1070. Several sources are forum posts or vendor pages, and they're marked where it matters.

## Map format

### Decided

| Question | Decision |
|---|---|
| Whose format | Our own. glTF as the level and a thin layer over standards were both turned down, because we'll have our own editor flow |
| Encoding | Text while working, binary from a final compile step, with one data model |
| Testing | Working maps load and play uncompiled, so testing doesn't wait for baking |
| Upgrades | Plain versioning, nothing fancy. We're internal, so the aim is only not to trip ourselves up |
| Geometry | Brushes and meshes are both map geometry |
| Placements | A reference plus that placement's position, rotation and scale. Those values affect only that placement. Editing the source item changes every placement, as expected. Static placements are baked in at compile |
| Entities | A name, a type, a mesh reference and a transform, plus typed properties passed to Luau. An entity can be a mesh, and the mesh is just the mesh |
| Names | Not unique. Reusing a name makes parts of one thing, which is the author's call |
| Behaviour | The format gives properties no meaning. Things like targets are a scripting decision left to the author |
| Reuse | Common containers hold reusable items, referred to by name, so file sizes don't balloon |
| Sky | A sky sphere and gradient horizon instead of a cube, where applicable, with a cloud layer on top. Indoor maps may not have one |
| Size | Chunking or tiling lifts map size limits, where applicable. Its details are still open |

### Suggested

- Missing baked sections have fallbacks: no visibility draws everything, and no lighting uses simple light.
- Baked data records what it was built from, so stale data is ignored.
- Text and compiled loads of one map give identical results, which makes a useful test.
- Bulk data, such as imported meshes, stays in binary files that text refers to. Floats must round-trip exactly.
- Containers are folders while working and packed files on compile, and they layer like `-game`. `engine_assets::FileSystem` already mounts in search order.
- Until the editor exists, test maps are generated by code. The BSP importer stays, because playing Quake is our regression check.
- `engine_map::Map` is still BSP-shaped, in `Face`, `TexelAxis` and `Tree`, so it has to change first.

### Why our own compilers matter

Our own format means `ericw-tools` can't bake our maps. Lighting and visibility compilers become ours to write, and much of what's below rests on them. This is the largest unbuilt piece.

### BSP limits, as a format

From `reference/quake/WinQuake/bspfile.h`, BSP29 has narrow `short` fields, fixed caps such as 8,192 leaves and 16-byte texture names, a fixed set of 15 lumps, and visibility that grows with the square of the leaf count. Compiling also throws the brushes away: they live in `.map`, not `.bsp`.

### What other engines do

| Engine | Level format |
|---|---|
| Unreal | Its own. [One file per actor while editing, embedded in the level on cooking](https://dev.epicgames.com/documentation/en-us/unreal-engine/one-file-per-actor-in-unreal-engine) |
| Source 2 | Its own. [`.vmap` is DMX, with half-edge meshes, and compiled data is split into separate files](https://developer.valvesoftware.com/wiki/.vmap) |
| Godot | Its own. [`.tscn` is text with a `format=` version](https://docs.godotengine.org/en/stable/engine_details/file_formats/tscn.html) |
| Bevy | [BSN arrived in 0.19, mostly written in code](https://alternativeto.net/news/2026/6/bevy-0-19-brings-next-gen-scenes-faster-rendering-contact-shadows-and-new-feathers-widgets/) |

## Materials and texturing

### Wants

- **Not PBR by default.** The human finds its look bright and samey. A material names its shading model, such as lit, cel, matcap or unlit.
- **About 8 slots a material,** shared by blended layers, like WoW's terrain, and extra maps such as specular and shadow. Too many would hurt, because each map is at least one read per pixel.
- **Mega texture,** specular maps, alpha blending and masking, texture filtering, and anti-aliasing that's cheap without being blurry.
- **Optional matcapping,** and cel shading.
- **Outlining and semi-outlining.** Inverted hull and post-process both stay for testing, and a combination is likely.
- **Inpainting,** in three senses, covered below.

Features may combine once they're chosen. Channel packing and flattening layers on compile are the obvious ways to cut cost.

### Today

There are four unrelated image types: world `Texture`, `AliasModel.skins`, `SpriteImage` and canvas pictures. Alpha means different things on each. Everything is RGBA8 `UNORM`, sampling is hard-coded to nearest, and there's no anti-aliasing.

### Findings

| Item | Finding |
|---|---|
| Mega texture | [id dropped it for id Tech 7 in favour of streaming](https://www.wikipedia.org/wiki/Id_Tech_7). Layers, decals and flattening on compile may cover most of the look |
| WoW layers | [Terrain chunks hold up to four layers](https://github.com/mangosArchives/Mangos-Zero-server-old/wiki/ADT-Files), and [one parser says newer clients allow 8](https://docs.rs/crate/wow-adt/0.7.0/source/src/chunks/mcnk/mcly.rs). How WMOs blend wasn't found |
| Matcap | [About one texture read](https://medium.com/playkids-tech-blog/matcap-render-art-pipeline-optimization-for-mobile-devices-4e1a520b9f1a). It ignores scene light, and [shifts with the camera](https://medium.com/@kumokairo/understanding-and-implementing-regular-matcaps-in-unity-10c6b78c6827), with a [world-space fix](https://kumokairo.github.io/posts/world-space-matcap-shading) |
| AA | [SMAA is sharper than FXAA at about 1-3%](https://thepcbolt.com/best-anti-aliasing/). MSAA suits forward renderers, with cost estimates from 10% to 50%. These are consumer sources. TAA is the blurry one to avoid |
| Outlines | [Hulls miss creases](https://discussions.unity.com/t/toon-outline-for-selected-edges-in-vr/858814) and [gap at hard edges](https://bugnet.io/blog/how-to-fix-outline-shader-artifacts), which matters for brushes. Post-process catches both but [needs tuning](https://kodeco.com/92-unreal-engine-4-toon-outlines-tutorial?page=3), and [forward renderers have no normal buffer](https://mert-kaan.is-a.dev/projects/outline-shader) |

### Inpainting

1. **Painting on surfaces in the editor,** tying into layers and baking.
2. **Filling and hiding seams automatically,** which we'd do anyway.
3. **Texture surface inpainting into geometry.** A stencil turns a flat wall into bricks, or a decal with writing carves its letters.

The third is detail only and doesn't change collision. Its main point is that carving normally leaves new surfaces with no texture, such as the sides and floor of a letter, and inpainting fills them.

Suggested: working maps keep the flat brush and the stencil, and compile does the rest. Relief uses a height grid, while carving traces outlines for clean edges. New surfaces default to projecting from the side, with an inner material as an override. True image inpainting can come later. Edges where a stamped face meets its neighbour are the hard part.

### To check

Decals, [hotspot texturing](https://developer.valvesoftware.com/wiki/Hotspot_texturing), [hex tiling](https://jcgt.org/published/0011/03/05/paper.pdf), [parallax](https://bentobaux.github.io/posts/parallax-mapping-with-self-shadowing), reflections, flow maps, triplanar mapping and fake rounded edges. [Doom 2016's decals](https://www.adriancourreges.com/blog/2016/09/09/doom-2016-graphics-study/) look like the biggest single gain for flat surfaces.

## Lighting

### Decided

The engine won't use one system for everything. The kinds of light are separate, and what matters is that they work together properly, including occlusion. A player casts a shadow and takes light from the environment.

| Kind | Examples | Approach |
|---|---|---|
| Fixed | Wall lamps | Baked, and featureful. Soft shadow heatmap, with crispness where needed |
| Limited motion | Swinging lamp, light on a rail | Baked along its known motion, blended at runtime |
| Bounced | Light filling a room | Baked, PRT-like |
| Moving | Rockets, flashlights | Live, in their own budget |
| Fixed micro | Torches | Probably a precompiled shader, and maybe particles |

### Findings

| Item | Finding |
|---|---|
| Shadow cost | Shadow maps add cost to a light. A shadowed point light means [six passes over the scene](https://github.com/APKiwiOrg/KhaozEngine/issues/1144). Unreal measured [three such lights at 14.89 ms, or 0.9 ms with caching](https://dev.epicgames.com/documentation/en-us/unreal-engine/movable-lights?application_version=4.27) |
| Precomputed shadows | The human's idea of compiling light angles. [Horizon maps](https://en.wikipedia.org/wiki/Horizon_mapping), [PRT](https://learn.microsoft.com/en-us/windows/win32/direct3d9/precomputed-radiance-transfer), which gives soft shadows only, and [compiled distance fields](https://dev.epicgames.com/documentation/en-us/unreal-engine/distance-field-soft-shadows-in-unreal-engine) |
| Crisp baked shadows | [Stored as a 2D distance field, sharp at low resolution](https://docs.unrealengine.com/4.27/BuildingWorlds/LightingAndShadows/LightMobility/StationaryLights) |
| Combining | Direct and bounced light must stay apart, or a moving object can't properly block a lamp. [Dimming the lightmap is imprecise](https://docs.unity3d.com/ru/560/Manual/LightMode-Mixed-Subtractive.html), and [shadow masks combine properly](https://docs.unity3d.com/ru/560/Manual/LightMode-Mixed-Shadowmask.html) up to about four lights |
| Direction | Baked light has to store direction for specular, for reflections that shift as you walk past a pillar, and for character shadows |
| Limited motion | Assassin's Creed [baked 4 to 11 keyframes](https://www.realtimerendering.com/advances/s2025/content/Advances%202025%20-%20Raytracing%20the%20world%20of%20Assassin's%20Creed%20Shadows.pdf). Far Cry 3 [relit PRT probes](https://gdcvault.com/play/1015957/Deferred-Radiance-Transfer-Volumes-Global). Crisp shadows may look doubled when blended |
| Moving objects | Probes for environment light. [Capsule shadows](https://dev.epicgames.com/documentation/en-us/unreal-engine/capsule-shadows-overview-in-unreal-engine) and [a dominant light direction from the bake](https://lousodrome.net/blog/light/2013/08/) |
| Many lights | [Clustered lighting](https://research.chalmers.se/en/publication/161725) lists only the lights touching each cell. We have a fixed list of 32 today |
| Fixed light features | [Cookies](https://docs.unity3d.com/351/Documentation/Components/class-Light.html), [IES profiles](https://docs.unity3d.com/Packages/com.unity.render-pipelines.high-definition@17.0/manual/IES-Profile.html) and area lights. Most of their cost is paid in the bake |
| Fog | [A grid fitted to the camera gives light shafts too](https://masterallarts.pages.dev/learn/threejs-from-zero/s4-05-volumetric-fog/), at [about 3 ms on a GTX 970](https://dev.epicgames.com/documentation/en-us/unreal-engine/volumetric-fog-in-unreal-engine). Height fog is the cheap option, with no shafts |
| Light in water | [Procedural caustics](https://developer.nvidia.com/gpugems/gpugems/part-i-natural-effects/chapter-2-rendering-water-caustics), shafts and depth-based tint. Absorption has no good source yet |

### Baked occlusion around objects

Decided: a tool generates a separate file for each mesh. Characters use one averaged volume, with minor per-body-part detail where it's cheap, for motion or weapon fire. Per-pose bakes are reserved for items baked into the model itself, as a long tool process.

### Stencil rays

The human's idea, and the preferred route for rays. An invisible stencil sits in a window, grate or canopy, working like a specular map. Colour tints the light and alpha blocks it, so stained glass passes light and its frame cuts it, even for a moving light.

- **Pieces and boxes:** each glass piece is a ray, and its frame, drawn black in the stencil, is its ray box. An extra authored line, say red, groups pieces into a box for occlusion. A tool reads those lines into a box list, and the runtime never sees them. The lines need their own layer or file, since panes can be red too.
- **Rays:** a short march along the view ray, reading the stencil. Depth stops it at walls. Air can read a blurrier mip, so rays stay chunky, and the same map can pattern the floor.
- **Occlusion:** uses the existing collision, per box, not per pixel, so there's no separate list of occluders. Rays must start past the glass and ignore clip brushes.
- **Blending:** a box fades between blocked and clear, so it doesn't snap.
- **Cost:** flat however detailed the glass is. The fog grid stays an optional high setting.

## Sky

Decided: horizons are gradients, as part of the sky sphere, which is high quality and cheap. A sky layer sits on top for clouds and the like, either pre-created or generated procedurally. That's the author's choice, per sky.

A [zenith-to-horizon gradient is about as cheap as a sky gets](https://hugodaniel.com/pages/pngine/docs/samples/skybox/). [Two scrolling noise layers](https://git.ritchiecunningham.co.uk/Rtch/bettola/commit/a1c214caec3632fe4aad57fc86b2085a87e5a4d9) make clouds on a dome, and [layered 2D noise can fake volume](https://godotshaders.com/shader/aaa-fake-volumetric-clouds/). Clouds [can pinch at the poles](https://godotshaders.com/shader/procedural-sky-blended-cover-wind-and-clouds/) unless noise is sampled by direction.

## Tiles

Decided: this is largely up to research, with efficient organisation and loading, so nothing is missing. It likely adds a coordinate grid to maps. The rule is that a player never hits an unloaded tile. Generally several tiles load, and details fade in with view distance.

Engines that do this share one shape:

| Part | WoW | Bethesda | Unreal |
|---|---|---|---|
| Grid | [64 by 64 tiles of about 533 yards, each 16 by 16 chunks](https://warcraft-rs.readthedocs.io/en/latest/formats/world-data/adt.html) | [4,096 unit cells](https://ck.uesp.net/wiki/UGridsToLoad) | [Cells of a set size](https://dev.epicgames.com/documentation/en-us/unreal-engine/world-partition---hierarchical-level-of-detail-in-unreal-engine) |
| Index of what exists | [WDT](https://warcraft-rs.readthedocs.io/en/latest/formats/world-data/wdt.html) | Worldspace records | Runtime hash |
| Loading around the player | Not found | [`uGridsToLoad`, default 5](https://ck.uesp.net/wiki/UGridsToLoad) | [Loading range](https://dev.epicgames.com/documentation/en-us/unreal-engine/world-partition---hierarchical-level-of-detail-in-unreal-engine) |
| Far stand-in | [WDL, low detail heights](https://warcraft-rs.readthedocs.io/en/latest/formats/world-data/wdl.html) | Distant LOD | [HLOD](https://dev.epicgames.com/documentation/en-us/unreal-engine/world-partition---hierarchical-level-of-detail-in-unreal-engine) |
| Always loaded | Not found | [Persistent references](https://en.m.uesp.net/wiki/Tes4Mod:Mod_File_Format/CELL) | Non-spatial actors |

For research to answer:

- **Size:** tile size, and a flat grid or stacked. One author suggests [a load range of at least twice the cell size, and 3-4 times for fast movement](https://www.strayspark.studio/blog/ue5-world-partition-deep-dive-streaming-hlod). The engine's top speed is 2,000 units a second.
- **Nothing missing:** the order things load in, with collision before visuals. The load ring comes from top speed and worst-case load time, plus a margin. Teleports and respawns must load their destination first. A safety net for a miss still has to exist, and any miss counts as a failure.
- **Crossing tiles:** who owns things on a boundary, and what happens to entities in tiles that unload.
- **Baked data:** seams in lighting, and visibility between tiles.
- **Coordinates:** tile plus local position, or [doubles with origin shifting](https://forums.unrealengine.com/t/what-if-i-need-coordinates-in-double-precision/361297). Origin shifting [has been hard with multiplayer](https://forums.unrealengine.com/t/what-happened-to-the-large-world-coordinate-system-feature-the-highest-voted-in-the-roadmap/63157). Today's positions are `f32`, on the wire too, and steps reach `DIST_EPSILON` at 262,144 units.
- **Servers:** a server holds tiles for every player, not one view. Entity culling fits here too.
- **Packing:** how tiles group into megachunks.
- **Culling:** what isn't visible isn't drawn, though it stays in memory. The world has no hard distance cutoff: visibility decides what's drawn, and distance only trims detail. Tiles need visibility between them.
- **Simulation:** online, the server pays that cost, not the player. Locally, entities that aren't active don't need simulating. Those with regular behaviour use a seeded PRNG, so they don't look reset when seen again. Long-running behaviour has to still make sense, such as an NPC sent to run somewhere.

## Pathing

Up to research, avoiding Bevy for now. Today there's no navigation data at all: monsters use `movetogoal`, which picks directions towards a goal, `path_corner` chains are authored by hand, and bots wander.

Decided as the main items:

- **Waypoint splines** for predefined movement, shown in the editor as a floating line with bubbles.
- **A regular navmesh,** good enough to keep enemies and NPCs clear of obstacles and walls.
- **The baseline:** they must properly pass through doorways and nav tunnels without trying to go through walls.
- **Upgrades come later,** such as jumping down or into water beyond chasing, where a cliff or drop-off is an obstacle, and getting on elevators.

Suggested, as a compile output: a navmesh per tile, and a coarse tile-level graph for long routes.

| Item | Finding |
|---|---|
| Tiled meshes | Recast and Detour's [TileCache updates a mesh by tile](https://doc.babylonjs.com/features/featuresDeepDive/crowdNavigation/v2Intro/v2WhatsNew/v2NavParameters), which suits our tiles |
| Links | [Off-mesh connections cover ladders, teleporters and jump pads](https://www.npmjs.com/package/recast-navigation). Upstream [stored them in one tile, so load order could break a link](https://www.github.com/recastnavigation/recastnavigation/pull/645). Whether that was fixed is unconfirmed |
| Agent sizes | [Unreal bakes a navmesh per agent size](https://forums.unrealengine.com/t/how-do-i-set-up-navmeshes-for-characters-of-different-sizes/280867/2) |
| Long routes | [A coarse route through zones, detailed only where loaded](https://www.gamedeveloper.com/programming/in-depth-walking-in-the-void), which also suits sleeping NPCs |
| Rust | [`landmass`](https://github.com/andriyDev/landmass) and [`polyanya`](https://docs.rs/polyanya) find paths. [`oxidized_navigation`](https://docs.rs/crate/oxidized_navigation/latest/source) generates meshes but is a Bevy plugin. [`recast-rs`](https://awesome.ecosyste.ms/projects/github.com%2Fwowemulation-dev%2Frecast-rs) needs looking at. Release dates weren't confirmed |

## Editor

Decided: the editor is in the tools category, and gets its own binary, possibly its own repo. Qt and C++ are out. Rust is now the leaning, as simpler even with some extra work, and C# is the fallback, with its findings kept below.

UI style: the flat Precision look of Campfire and Scopework. Campfire is Rust with `iced`, using Monaspace, a custom title bar and split panels. Scopework is Rust with `eframe`, which is `egui`. So both toolkits are already in use, and the viewport test decides between them.

This is more than an editor: it's the development platform, even if only the editor is built now. Claude must be able to drive it, through both a command line and MCP, because it's needed for testing, mapping and map testing, so things can be added and changed quickly. Scopework's JSON command line and Campfire's rule that agent tools call the same operations as the UI are the patterns to follow.

Workflow: a simple and an advanced design. The main workflow goes through prefabs, such as ramps, stairs, railings, portals and maybe prefab entities, so things are quickly placed and built. Advanced options stay available, including Luau scripting, entity building and all the rendering features here.

Suggested: format reading, brush operations and compile stay in a library apart from the UI, so a shell can be swapped later, and every edit is a named operation that the UI and agents both call. Campfire's `iced` draws in software through `tiny-skia` and `softbuffer`, so sharing a window with a Vulkan viewport needs proving.

C# fallback findings:

| Part | Finding |
|---|---|
| UI framework | [Avalonia is cross-platform](https://avaloniaui.net/winui-compare) and its XAML is close to WPF's. WinUI 3 is Windows only. That comparison is Avalonia's own. WPF wasn't compared directly. Docking, property grids and Avalonia's licence still need checking |
| Bindings | [Interoptopus generates C# from Rust](https://docs.rs/crate/interoptopus/latest). `csbindgen` and `uniffi` weren't confirmed |
| Viewport | [`NativeControlHost` hosts an `HWND`](https://docs.avaloniaui.net/docs/app-development/native-interop), and WPF's `HwndHost` is its equivalent. [It sits above or below the UI, with no transparency](https://docs.avaloniaui.net/docs/platform-specific-guides/windows), so panels can't overlap it. Vulkan on a child `HWND` wasn't confirmed |
| Engine work | The renderer has to accept a window it didn't create, since `engine_platform` owns the window today |
